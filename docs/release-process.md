# Release process

## Рабочий цикл

1. Разработка и промежуточное тестирование выполняются на локальных Functional Test-сборках.
2. После стабилизации версии формируется отдельная release-сборка с финальными метаданными версии.
3. Release-сборка проходит итоговую проверку как готовый portable EXE.
4. Исходники, changelog и документация приводятся в состояние выпускаемой версии.
5. Для зафиксированного состояния репозитория создаётся Git tag вида `v1.0.3`.
6. На основе этого тега создаётся GitHub Release `Owl-IN ServiceKit 1.0.3`.
7. К Release прикладывается **тот же EXE, который прошёл итоговую проверку**.
8. Для опубликованного бинарника фиксируется SHA-256 и сверяется с локально проверенным файлом.

## Текущий тестовый бинарник

Текущий EXE относится к Functional Test 77 и **не считается публичным release candidate**, потому что внутри приложения ещё отображается FT77.

```text
Owl-IN-ServiceKit-1.0.3.exe
SHA-256: 7b7c1843b437ad341be2ffe5abe525264acfbd7b0643e854e3c8ba29ffb97497
Статус: test artifact / FT77
```

Перед первым публичным Release 1.0.3 нужна отдельная release-сборка на той же стабильной базе: без пользовательской маркировки Functional Test, с отображением `Release`. Внутренний build number можно сохранить для диагностики, но он не должен выглядеть как тестовая версия для обычного пользователя.

После этой сборки EXE тестируется повторно и получает новый SHA-256. Только новый проверенный бинарник идёт в GitHub Release.

Исходный архив стабильной базы:

```text
OwlIN-ServiceKit_1.0.3-Functional-Test-77.zip
SHA-256: 853ba7a61d513e0354b9c20724a9e933fc64491b61413ac33e3b543c5e0c9440
```

## Важно

Официальный EXE не пересобирается после итоговой проверки без повторного тестирования. В GitHub Release должен попадать тот же бинарник, который был проверен локально.

Готовые EXE не коммитятся в исходники. Они размещаются только в GitHub Releases.
